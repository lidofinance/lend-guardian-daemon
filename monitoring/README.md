# Guardian monitoring receiver

The daemon posts every SDK event to `EVENTS_URL` ([daemon/README.md](../daemon/README.md), Events and liveness). This receiver takes them on `POST /events`, keeps Prometheus metrics under the names of the previous Guardian daemon, prints each non-routine event as a JSON record with a level and a message, and answers readiness from the daemon's progress. It runs beside the daemon as its own container from its own image. When the pod names the Guardian registry and the RPC endpoints, it also reads the [delegate's balance](#delegate-balance), the one value it takes from the chain and not from the events.

| File                         | Role                                                                                                                                                        |
| ---------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| [`main.ts`](main.ts)         | Configuration, build info, the servers and the timer of the balance read.                                                                                   |
| [`events.ts`](events.ts)     | The event names and their levels, bound to `DaemonEvent` of [`daemon/main.ts`](../daemon/main.ts); parsing, scrubbing and the format of every printed line. |
| [`receiver.ts`](receiver.ts) | What each event updates, the printed record and the freshness state.                                                                                        |
| [`metrics.ts`](metrics.ts)   | The registry.                                                                                                                                               |
| [`balance.ts`](balance.ts)   | One read of the delegate and its balance from the RPC endpoints into its gauge.                                                                             |
| [`server.ts`](server.ts)     | `/events` on the loopback port; `/metrics`, `/health`, `/ready` on the other.                                                                               |
| [`Dockerfile`](Dockerfile)   | The image, built from the repository root.                                                                                                                  |

## Run

```bash
docker login docker.io --username lidofinance
docker build -f monitoring/Dockerfile -t guardian-monitoring .
docker run --rm -p 9464:9464 -e GUARDIAN=0x… -e MODE=signal -e CHAIN_ID=560048 guardian-monitoring
```

The receiver takes events only on the loopback interface, so the daemon and the receiver must share one network: in Kubernetes the receiver is a second container of the daemon's pod, and with Docker the daemon runs with `--network container:<receiver>`. The daemon then posts to `EVENTS_URL=http://127.0.0.1:9465/events`.

Or without an image, from the repository root: `node monitoring/main.ts`. The receiver imports only the event types of the daemon and the SDK, which Node erases, so the image holds `monitoring/` alone; `monitoring/package.json` lists its only runtime dependency. The build arguments `BUILD_VERSION`, `BUILD_BRANCH` and `BUILD_COMMIT` go into `build-info.json`, `unknown` when not given.

## Configuration

| Variable                        | Default | Meaning                                                                                                                                          |
| ------------------------------- | ------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| `MONITOR_PORT`                  | `9464`  | The port of `/metrics`, `/health` and `/ready`, on every interface.                                                                              |
| `MONITOR_EVENTS_PORT`           | `9465`  | The port of `POST /events`, on the loopback interface only, because an event can make the daemon look ready. It must differ from `MONITOR_PORT`. |
| `MONITOR_EVENT_TIMEOUT_SECONDS` | `900`   | `/ready` is 503 after this long without an accepted event.                                                                                       |
| `MONITOR_CYCLE_TIMEOUT_SECONDS` | `3600`  | `/ready` is 503 after this long without a cycle that made progress: one that ends `attested`, `observed` or `nothing-due`.                       |
| `GUARDIAN`, `MODE`, `CHAIN_ID`  | empty   | The daemon's identity as the pod configures it; labels of `lido_lend_guardian_daemon_info`.                                                      |
| `GUARDIAN_SIGNALS`              | none    | The daemon's registry of the same name, for the balance read. Set it together with `RPC_URLS`; the read also needs `GUARDIAN`.                   |
| `RPC_URLS`, `RPC_URLS_FILE`     | none    | The daemon's secret of the same name: comma-separated HTTP or HTTPS URLs, or the file that holds them, for the balance read.                     |

The daemon pauses six minutes between cycles and reports every RPC request during one, so the event window outlasts the pause; a cycle with screening and a full send budget ends within the hour, so the cycle window outlasts a cycle. A daemon that keeps making RPC requests inside a cycle that never ends trips the cycle window, which event silence alone would not show. So does a daemon whose cycles all end `stale`, `incomplete` or failed, as when the screening service is down.

## Delegate balance

The daemon reads no balance and its events carry none, so a delegate that runs out of gas shows only as failed transactions. With `GUARDIAN_SIGNALS` and `RPC_URLS` set, the receiver reads the balance itself. At start and then every minute, it asks the endpoints in their order and waits up to ten seconds for each answer. From the first endpoint that answers, it reads `getDelegate(GUARDIAN)` of the registry and `eth_getBalance` of that delegate, both at the latest block. It keeps the balance in `lido_lend_guardian_daemon_delegate_balance_wei` with the time of the read beside it.

- **No address to copy.** The delegate comes from the registry at each read, the address the daemon also requires of its signer. A rotation of the delegate needs no change to the receiver, and the series of the previous delegate is dropped at the first read after it. `GUARDIAN` and `GUARDIAN_SIGNALS` are the daemon's own values.
- **Off by default.** Without both variables the receiver makes no RPC request. One without the other, a `GUARDIAN_SIGNALS` or `GUARDIAN` that is not a 20-byte hex address, both forms of `RPC_URLS` at once, a file that cannot be read or a URL that is not HTTP or HTTPS stops the start.
- **A failed read changes nothing else.** When no endpoint answers, the receiver prints `monitor.balanceFailed` with the reason of each endpoint by its position in `RPC_URLS`, never by its URL: the HTTP status, the node's JSON-RPC error code, an answer without a result, a registry without a delegate for `GUARDIAN`, or the error of the request. The gauge keeps its last value, and its timestamp shows the age. Events, the other metrics and both probes do not depend on the read.
- **The receiver holds no signing key.** In a pod that mounts the daemon's secrets into every container, give the receiver the path of the RPC URLs only.

## Endpoints

`POST /events` is served on `MONITOR_EVENTS_PORT`, the other endpoints on `MONITOR_PORT`.

| Endpoint       | Answer                                                                                                                                                                                                                                                      |
| -------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `POST /events` | One JSON object per request, `Content-Type: application/json`, at most 32 MiB. 204 when accepted; 400 for a body that is not JSON, not an object or names an unknown event; 405, 413, 415 otherwise.                                                        |
| `GET /metrics` | The Prometheus exposition.                                                                                                                                                                                                                                  |
| `GET /health`  | 200 while the receiver serves; the liveness probe.                                                                                                                                                                                                          |
| `GET /ready`   | 200 while the daemon is fresh: an event within the event window and a cycle that made progress within the cycle window; 503 before the first such cycle and after either window lapses. Both probes return the version, `lastEventAt` and `lastProgressAt`. |

An accepted event is counted, its metrics are updated, and the record is printed before the response. A payload field that is missing or malformed leaves out only what needs it: a cycle, RPC request or screening request without both `startedAt` and `finishedAt` still counts, without a duration or a time. The event itself always counts. The receiver does not retry, queue or acknowledge: the daemon posts once and moves on, so a lost event is invisible here; `lido_lend_guardian_monitor_last_event_timestamp_seconds` shows silence.

## Records

One JSON line on standard output per accepted event, except `rpc.requestStarted` and a successful `rpc.requestFinished`, which are thousands per cycle and are counted only: `timestamp`, `sequence` (the receiver's own counter), `level`, `event`, `cycleId` when the event has one, `details`, the payload without `event`, `cycleId` and `params`, and `message`. Every line, the receiver's own included, has a `message`: the event name, or `<event>: <error message>` when the line has an `error` with a message, at the top or in `details`; it is built after the scrub, and a `message` field of the payload stays in `details`. Every line, the receiver's own `monitor.started`, `monitor.failed` and `monitor.balanceFailed` included, goes through one scrub: a field whose name contains `key`, `secret`, `token`, `pass`, `private`, `credential`, `auth` or `cookie` is dropped, URLs in text are replaced by `[url]` and strings are bounded to 500 characters. Levels: `cycle.failed`, `transaction.failed`, `schedule.cycleNotStarted` and `schedule.restartBudgetExhausted` are `error`; `transaction.replaced`, `transaction.retry`, `nonce.cleared`, `rpc.answersDiffer` and a `screening.requestFinished` with an `error` are `warn`; the rest is `info`. Of the receiver's own, `monitor.failed` is `error` and `monitor.balanceFailed` is `warn`. The daemon's `daemon.failed` goes to its standard error, never to the receiver.

## Limits

The daemon's signer address and settings are in its `daemon.started` record, which the receiver prints but turns into metrics only for the build; a receiver started later never sees it. The running image and its digest are in `kube_pod_container_info`. `rpc_error_code` stays empty for an error without a numeric code, such as a timeout. The `http_rpc_*` and `rpc_request_total` metrics count the daemon's requests only: the receiver's own balance reads are not among them. Counters reset with the receiver process, which also forgets the deposits of `risk_decision_timestamp_seconds`, and an event lost on the way is missing from every metric except the post totals.

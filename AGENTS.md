# guardian-daemon-sdk: agent guide

This repository contains the Guardian cycle SDK and its partner reference application. The caller implements `ScreeningProvider` and supplies its configured signing/RPC client and cycle loop. The SDK signs and submits registry reports and heartbeats. Transaction deduplication and concurrency belong to each screening provider. Vendor integrations and production operating tools belong to the consuming application. Read this file fully before editing; `CLAUDE.md` points here.

## Specification boundary

The approved contract implementation is the source of truth for protocol behavior. Mandatory specification review checks the actual registry, market-controller, collateral-activation and core implementations and call paths, interfaces and types. Obtain the reviewed source baseline from the maintainer. Documentation, copied ABIs, SDK behavior and tests alone are not substitutes. Every protocol claim affected by a spec edit must have a concrete contract-source reference in the review/change ledger; record the source baseline without Git access. If spec or SDK behavior conflicts with the contracts, resolve that discrepancy against the code rather than documenting the SDK's behavior as protocol truth. Distinguish offchain Guardian obligations from checks the contracts actually enforce; absence of an onchain check does not cancel an offchain obligation. Do not change contracts to make a documentation change fit.

The main body of `docs/guardian-specification.md` contains only implementation-independent Guardian behavior and compatibility requirements. Retain an explicitly illustrative appendix in the same document: it describes one possible implementation through language-neutral pseudocode, abstract types, inputs and algorithms. The appendix must satisfy the main requirements without making its particular algorithm mandatory for every implementation.

Neither the main body nor the appendix prescribes a programming language, runtime, environment-variable names, configuration-file format, secret escaping/redaction, log or metric layout, retry budgets, or one application's nonce and fee management. Keep those choices, SDK internals, object copying or freezing, language-specific value representations, and SDK-specific validation or error handling in code, API documentation or implementation guides. Protocol constants, compatibility encodings and behavioral preconditions remain specified; they are not deployment settings. Do not remove the pseudocode appendix as part of cleaning the specification.

Version 0.1.0 was already shared with partners, so minimize changes: preserve structure, terminology, ordering and the pseudocode appendix. Make only necessary, localized corrections for demonstrated errors, consequential ambiguity or compatibility. Do not rewrite, rename, renumber or reformat unaffected text, or add requirement IDs throughout the specification. Each proposed change needs a concrete reason and a statement of whether it changes required behavior. SDK implementation choices alone do not justify a specification change; do not bulk-import the daemon/SDK additions.

`docs/guardian-specification.md` is the canonical specification, version 0.2.0. Its change note is for implementers migrating from the previous published version and lists only requirements or compatibility behavior that changed relative to that version. Do not list editorial work or clarifications of requirements that already applied. Consuming applications and contract documentation contain version/hash references instead of independent copies. Update those references together when the specification changes. Publication and immutable Git revision links remain maintainer actions. Moving document ownership does not authorize changing requirements. Preserve the reviewed layout: this file is excluded from automatic formatting so unrelated table and prose formatting stays intact.

Monitoring, cycle-record retention and operator alerts are outside the Guardian specification's scope. Maintain those operational requirements in the consuming application; do not reintroduce them as protocol or SDK conformance requirements.

## Layout

- `src/core/index.ts` is the public core entry point. `Guardian.cycle` runs one complete iteration over `buildScanPlan`, `discoverCandidatePositions`, `reconstructWork`, `screenWork` and `signalAndHeartbeat`; the individual phase methods remain public for inspection and focused integration. `Guardian` owns phase orchestration and returns outcomes for the caller to handle. `types.ts` holds shared position identities, report targets and supply anchors; `screening-provider.ts` defines the provider contract; `Screened.fromAnswers` in `outcomes.ts` validates provider answers and derives reports; `digest.ts` commits coverage.
- `src/contracts/` contains `Markets` for core/controller evidence and `GuardianSignals` for registry reads and writes. `Markets` owns the specification's candidate-discovery and contributor-reconstruction algorithms together with their contract calls and lifecycle interpretation. `GuardianSignals` owns previous-heartbeat recovery together with registry calls and events. Their decoded `Position`, `LifecycleEvent`, `Activation` and `SupplyLog` shapes are private implementation details; `Guardian` owns the cycle decisions that compose both contract layers.
- `src/chain/` contains `BaseRpcProvider`, `ViemRpcClient`, transport types and log ordering. Contract access uses this shared chain layer; ABI fragments live at the repository root. `viem-transport.ts` owns one HTTP attempt, the fallback between endpoints and the optional comparison of logs between providers.
- `abi/` contains one minimal ABI fragment module per contract, named for the registry, core or market-controller role; contract readers import these modules directly. Include only SDK-used functions and events, preserving contract parameter, event field and tuple component names in human-readable signatures. Test-only entries belong in tests. Conformance tests compare the wire layouts with the pinned fixture ABI subsets.
- `src/common/types.ts` defines shared public values such as `Address`, `BlockRef` and `TxHash`, plus the internal address-lowering function. The public types intentionally remain independent of viem.
- `src/common/validation.ts` owns shared internal numeric range validation and the non-null object guard. Guardian, RPC clients and screening validation use these helpers; domain-specific decoders and rules stay with their owners. Keep the helpers out of the public exports; `example/env.ts` separately parses and validates environment strings without importing SDK internals.
- `example/screening-adapter.ts` contains the incomplete `UnconfiguredScreening` placeholder and the `screening` instance imported by `daemon.ts`. Readers adapt that instance to connect their provider; `main()` takes no arguments and is not an exported integration API. Each production provider implements the SDK's `ScreeningProvider`; the SDK does not prescribe its deduplication or concurrency strategy.
- `example/env.ts` owns on-demand environment reads and validation. The launcher uses `import * as env`; internal parsing helpers remain unexported. Importing the module must not read configuration or signing material.
- `example/daemon.ts` keeps configuration, scheduling and inline error handling in `main`, and delegates one complete iteration to `Guardian.cycle`. Keep the scheduler's `try/catch` inline rather than introducing an attempt-result wrapper. `Guardian` owns report grouping, plan checks and confirmation order; `GuardianSignals` encodes contract calls; `RpcClient` owns the signing account, broadcast and generic receipt checks. The example defaults to observe without reading a signing key or creating a wallet. `UnconfiguredScreening` returns incomplete results, which the SDK handles normally; do not add provider-class readiness checks to the example. A failed attempt is followed by another one after a delay. An attempt that reached sending, which the example learns from the `transaction.*` events, first clears the signer's pending nonces with `Guardian.clearPendingNonces`; an error of that recovery ends the process for operator reconciliation. See `example/README.md` for provider wiring and application limits.
- `scripts/check-surface.ts` follows declarations from the public `/core` entry point and permits only `EIP1193Parameters` and `PublicRpcSchema` in the RPC declaration and rejects other exposed viem types.
- `tests/core/` drives the core over a scripted node. `tests/example/` covers the launcher modes and incomplete screening placeholder.
- `tests/conformance/` is the standalone contract and submission evidence package. Its pinned artifacts have their own recorded revision and build provenance; they are not evidence that a live deployment or the current contract checkout has identical bytecode.
- `docs/guardian-specification.md` is the normative contract. Audit planning stays in the ignored local `audit-scope.md`; do not link it from partner documentation or include it in the package.

A module under `src/` never imports from `scripts/`, `tests/` or `example/`. The package exports `/core` for SDK contracts with the standard RPC schema and `/clients` for supplied implementations; it has no root tracker or `/adapters` entry point.

The maintainer explicitly keeps the example's logging simple: do not add secret collection, URL rewriting or a credential-redaction layer to it. Those mechanisms belong to a production runner, not this reference example.

The example supports viem's `mainnet` and `hoodi`, both with 12-second slots. `env.chain('CHAIN_ID')` selects `1` (mainnet, the default) or `560048` (Hoodi) and rejects other values. Both clients and Guardian use the selected chain; RPC endpoints remain configurable through the transport. Keep error output direct with `console.error`, without custom viem error parsing. The SDK itself retains configurable chain identity and slot duration.

## Readability and TypeScript review

The shared code-quality policy uses `const` by default and `let` for state the algorithm advances. Use explicit `while` loops for state transitions and `while (true)` for body-controlled completion; do not use conditionless `for` loops, recursive rewrites or mutable wrapper objects just to avoid reassignment. Keep the main algorithm visible, helpers with their owning class, and extract only substantive subproblems. Function-size exceptions must have a concrete readability reason and an accurate description of their ESLint scope.

Review `src/` and `example/` manually against [STYLE_GUIDE.md](STYLE_GUIDE.md), alongside the compiler, ESLint and Prettier checks. The guide owns the detailed TypeScript rules; keep it, `tsconfig.json` and `eslint.config.js` consistent. External style guides inform the review, but their preferences do not silently replace this repository's rules. Passing lint alone does not establish readability or sound design.

Check whether names express domain roles and units, the main flow reads in order, functions and modules have clear responsibilities, and helpers reduce the effort needed to follow that flow. Review precise state types and boundary validation, ownership of mutable values, asynchronous ordering and concurrency, failure propagation, public API explanations, dependency direction and unnecessary abstractions. Apply the same standard to example code a partner may copy. Record each actionable finding with its location, the applicable rule or concrete comprehension problem, the smallest useful change and any behavior or API impact. Do not split functions just to satisfy a size metric or change behavior as a style fix.

## SDK contracts

`GuardianSetup` distinguishes `mode: 'observe'` from signal mode (the default). Observe requires no private key or expected delegate, checks chain and Guardian membership, and refuses `signalAndHeartbeat` with `submission-disabled`. Signal keeps all authorization checks.

Signal mode requires `client: RpcClient` and `expectedDelegate`; the client exposes its actual signing account as `signer`. `ViemRpcClient` adapts configured public/wallet clients and inherits shared reads from `BaseRpcProvider`. Guardian never constructs another library client. Observe takes `RpcProvider`; a base client over a raw `request` function is sufficient. `maxLogBlockRange` belongs to the client. Network identity and slot duration belong to Guardian; its activation lookback remains seven days, derived from that slot duration.

Pass configured viem clients directly to `ViemRpcClient`; callers must not copy clients or override request/signing methods to satisfy SDK types. The `/clients` entry point deliberately uses native viem `PublicClient` and configured `WalletClient` types; `/core` retains SDK value types and uses viem’s standard JSON-RPC schema for `Transport`. This type dependency does not require a viem runtime client. Keep the request result tied to its method; do not expose an independently overridable result type. Do not recreate library method/argument/result interfaces or re-export the viem adapter from `/core`. Configure the wallet's account and chain at creation; preserve its configured signing method and transport policy.

`ViemRpcClient.send` owns the attempt loop, deadline, fee cap, signing, raw broadcast, observations and error handling. Private phases own substantive operations: `#prepare` preserves the call and replacement nonce/fees, `#waitForInclusion` reconciles submitted hashes around the native waiter, and `#confirm` waits for depth and verifies fresh canonical evidence. Receipt lookup and the fee-increase calculation are shared private helpers. Keep per-send state local; do not reintroduce `Submission`, forwarding wrappers for individual library calls/events, a custom receipt-polling loop, or the old test submitter contracts. The replacement interval is `replacementTimeoutMs`; inclusion and confirmation waits are separate, and an included transaction is not replaced merely because depth is slow. Review method ownership and state before implementation and verify actual deletions afterward.

`Guardian` groups reports by kind and market, checks the plan before every batch and during the shared full-depth wait, stops on stale and rereads canonical receipts before heartbeat. It validates the client's `sendTimeoutMs` at construction, requiring at least `txConfirmationBlocks + 1` slots, and bounds the shared wait of each report kind with it; when that budget ends first the attempt stops with `report-confirmation-timeout`, its reports already included. It confirms the heartbeat before returning `Attested`. `Markets` and `GuardianSignals` own contract calldata and event decoding; the client owns generic reads, signing and delivery. Send errors propagate unchanged, without revert-name classification or an SDK recovery policy. Keep signing material out of diagnostics; `onEvent` is the application hook, not a logger. These boundaries supersede the earlier direct-private-key setup.

The screening request is isolated from `Work`: `Guardian.screenWork` gives the provider frozen copies of the request, anchor array, individual anchors and report block, and pairs answers with the original anchor order. Keep these protections; TypeScript `readonly` alone cannot protect the heartbeat's coverage. Mutation and retained-reference guards live in `tests/core/screen.test.ts`.

Screening evidence may be omitted, `undefined` or `null`; a supplied identifier must be a nonempty string. Missing, malformed or incomplete results stop the attempt before submission. Provider failures must not become clean results.

The `logQuorum` option of `createViemRpcTransport` is optional runner policy for several independent providers, not a specification requirement. There is one transport: do not add a second factory, a provider cooldown or other state kept between requests. It compares `eth_getLogs` only, because that is the read a lagging provider answers incompletely without an error; an explicit check of the method sends every other request to viem's fallback, so do not route by transport method filters. With the option the transport is a viem custom transport around that fallback, so viem no longer keeps the requests of a filter on the endpoint that created it; the SDK uses no filters. Keep it that small: do not add per-method rules or comparison of other requests without a maintainer decision. `logQuorum` is at least two and at most the number of URLs; whether it is a majority is the runner's choice. Every provider is asked at once and awaited until it answers or reaches `timeoutMs`. A provider that fails or sends an invalid list is absent rather than dissenting. Logs are returned when a quorum returned them alike, whatever their order, and they include every log that any other provider returned, so a provider that only lacks logs is reported and does not reject the read, while a log that the quorum lacks rejects it. Every difference is reported through `rpc.answersDiffer`, accepted reads included. The example enables the option through `RPC_LOG_QUORUM`. Agreement cannot detect a log that every answering provider omits, so two providers that lack the same log form a quorum while the third does not answer; keep that limit stated wherever the transport is described.

ABI-filtered event queries decode every returned log and stop on one that does not decode. Discovery reads the window's supplies forwards, a piece at a time. For each piece it reads the lifecycle events of the piece's controllers and of the candidates' controllers from the first unread block through the piece's last supply, never once per supply or block, and pairs every supply in memory with the log before it; after the last piece it reads the candidates' controllers through the report block. It holds one piece of logs and the candidates found so far, not the window's logs. It also discards a candidate whose newest event in the window leaves it not base-due at the report block, the check reconstruction would make first, so a lot withdrawn, activated or extended since its supply costs no history walk. `maxLogBlockRange` limits every inclusive range. `Guardian.cycle` and `reconstructWork` take an optional `earlierWork`, such as a stale outcome's `work`: a position of it keeps its anchors when that work was reconstructed from the plan's previous heartbeat at a report block that is still canonical and the position's controller logged no event for it since, which one read per controller checks; every other position is walked, and discovery always reads the window again, so the work is the one a full reconstruction finds. A range whose read fails is read again in halves, down to one block, because a provider's log limit or the transport's response limit refuses a range that holds too many logs, and the rest of its static range is read at the size that worked; a block that fails alone propagates its error, and every failed attempt stays visible in the transport's events.

## Toolchain

- Node 24 or newer (`.node-version`). TypeScript runs natively with type stripping. Only erasable syntax is allowed: no enums, namespaces or parameter properties.
- `npm run check` runs typecheck, lint, format check, a clean build, the public surface check and all tests. Run every stage before finishing a change. `test:core`, `test:example` and `test:conformance` select the corresponding suites. Tests use local fixtures, scripted nodes and isolated Anvil processes and make no external requests. Contract conformance requires Anvil 1.7.1 on `PATH` or selected through `ANVIL_BIN`.
- `npm run build` removes `dist/` and emits JavaScript and declarations from `src/` and `abi/` into `dist/src/` and `dist/abi/`; no output of a removed module survives. `prepare` builds on dependency installation. The package ships `dist/`, `src/`, `abi/`, the specification, reference example and standard package metadata, README and license, with `/core` and `/clients` entry points. Tests, verification scripts and the local audit scope are outside the package.
- The package is `private` until registry publication is arranged. The maintainer has decided the SDK repository will be public; installation uses the public source without credentials. No deploy key is needed. Never create, request or check `SDK_DEPLOY_KEY`.
- ESLint enforces the mechanical rules of `STYLE_GUIDE.md`; Prettier owns formatting. Do not add `eslint-disable` comments. Format and lint changed files while iterating, then run the full check.
- Code, comments, tests, documents and reports are written in English. Use the checklist under `.claude/skills/code-quality/SKILL.md` for code changes.

## Working rules

1. **Git and credentials belong to the maintainer.** Do not run Git or GitHub commands, including read-only checks, staging or commits. Do not inspect repository settings in a browser, keys, secrets or environment values. Ask the maintainer for the specific result or action needed. Local file changes and checks may continue independently.
2. **Implement the specified behavior.** Do not add stop conditions, exemptions or shortcuts that change Guardian policy without the maintainer's decision. The caller owns provider policy, credential provisioning and operational behavior; the configured RPC client owns signing and generic delivery, while Guardian owns report sequencing. `GuardianSignals` receives its read or signing client once and sends calls directly with `SendOptions`; do not pass a sending callback through each contract method.
3. **No new data sources without approval.** The core reads only what the Guardian specification names. New providers, endpoints, RPC methods or evidence sources require a maintainer decision.
4. **No hardcoded deployment bindings.** Deployment addresses and configuration come from the caller. Interpret chain evidence through its ABI, rather than identifying a deployment by an invented address list or fingerprint.
5. **Keep responsibilities separate.** Screening belongs to `ScreeningProvider`; core/controller evidence belongs to `Markets`; registry evidence and calls belong to `GuardianSignals`; generic signing and network mechanics belong to `RpcClient`; cycle and report sequencing belong to `Guardian`. Pacing, retries across cycles, alerting and credential provisioning belong to the caller.
6. **Keep failure visible.** A missing screening answer is not a clean decision. A node fault must not become a contract refusal, an empty result or cached success. Structured fields of SDK events identify an endpoint only by `rpcIndex`. Error objects keep viem's form, including those the SDK transport creates and those carried in an event's `error` field: they name the endpoint URL and the request. Credential redaction belongs to the integrating application’s logger.
7. **No scope creep.** Define interfaces first and justify each new module, type, method, field and option before implementing it. Add only elements needed by the task; do not add a helper before its first caller, an option nobody uses, a forwarding-only wrapper or a replacement for a dependency feature. When an abstraction has no concrete purpose, remove it.
8. **Use declared dependencies.** Hashing, ABI encoding and decoding, and address or hex operations come from viem. Before writing a utility, check the dependency and identify what is missing. Shared public value types are defined here; the standard JSON-RPC request schema is reused from viem rather than rewritten.
9. **Preserve acceptance evidence.** Keep existing behavioral tests unless the maintainer requests the behavior change. Add tests at the layer that observes the behavior, with independently stated expected results. Do not weaken assertions to make a change pass.
10. **Preserve data.** Never delete or rewrite caches, datasets, fixtures or benchmark results. Historical local data is outside the package and is not a cleanup target.

Conventional Commits are used, but the maintainer makes commits. A change is complete when the implementation and API documentation agree, changed code meets the manual readability rules, affected phase mappings and specification links are current, relevant acceptance checks pass, the full check passes, SDK-owned findings remain recorded, and no secret or historical data has been exposed or lost.
